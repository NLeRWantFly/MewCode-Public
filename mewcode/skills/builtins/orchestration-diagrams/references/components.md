# 编排组件与边界

## 阶段节点

- 规划 plan：只读调查、澄清输入、拆分方案；不是实现节点，不负责修改业务文件。调查有界：批量取得元数据，加上明确数量的代表样本；逐页、逐项的全量处理交给 implement 或批量循环。
- 实现 implement：在已授权范围内执行和产出；目标中写清输入、允许改动、交付物及验证方式。
- 汇总 reduce：整合上游成果、形成最终说明；输出完成不等于交付验收通过，不能覆盖上游未通过的审计，也不自动授予写文件权限。
- 审计 audit：按已确认标准检查证据并提交结构化 verdict。需要返修时设置 audit_target 指向实现节点，max_audit_retries 为 1–10；单向 fail 分支和有限返修不是一回事。
- 判定 decision：作条件评估；在通用循环的检查点用 SubmitLoopDecision 提交 EXIT / CONTINUE / BLOCKED。缺证据不是 PASS。
- 门禁 gate：运行到此处由运行器发出人工选择并等待明确答复，不由模型自行宣告通过。开跑前确认不替代此处确认；暂停或取消不执行该路径后续节点，选择继续也不把失败审计改为通过。运行中节点若确需提问，只暂停所在分支，其余独立分支可继续。

## 连线、分组与循环

- 普通依赖 always：上游完成后才可调度下游；pass / fail：按判定结果选路，未走分支不是失败。卡片位置、编号和自动布局都不决定执行顺序。
- 受阻备用路线：`on_blocked: fallback` 会按 `fallback_node_ids` 调度备用节点；每个目标都必须存在且不能是自身。
- 并行：默认串行；meta.parallel=true 时同批全部为可确认只读的普通角色节点才并行，并由运行器进一步收紧工具。门禁、循环、返修、委派和写入节点串行；outputs 不相交只是一项声明，尚不构成 Bash 写入隔离。
- 分组 canvas_groups：普通子阶段会折叠为父节点的执行约束，不一定分别调用模型；带条件分支或属于循环的子节点保留调度身份。视觉层级不等于子代理。
- 循环 loop：从检查点返回入口的显式回边，配套 meta.loops。需单入口、检查点出口和验收条目；最终汇总在循环之外。新循环默认 control_mode=team，Token、累计时长、修订轮数不作硬停止条件；只有用户明确选择 strict 才强制累计限额。旧严格合同不在用户不知情时迁移。
- 验收与退出：全部条件有通过证据才 EXIT。team 模式中，普通缺证据（包括 UNKNOWN）应 CONTINUE 补齐，可用 repair_node_ids 指定返修成员；确实需要用户选择、授权或提供无法取得的材料才 BLOCKED 并填写具体 question。持平或一次退步不代表失败，重复相同证据无进展时暂停说明原因，不得谎称通过。
- node_max_iterations 默认 40，reviewer_max_iterations 默认 12，均可设 4–200，用于执行分段，不是批量工作项数量。team 模式中宿主持久化进度确有推进则接续下一批；无进度由主模型提案、当前配置的审核模型选择有限诊断/接续路径，权限、合同或外部依赖缺失必须给出具体问题。不可用无限重试替代缺失能力。未完成结果不能直接当成功输入传给下游；继续先接续最早未完成节点。历史停止文字不是本次派发的禁止令，但实际权限与用户限制仍有效。
- 审计返修可接受“解决数大于新增数”的净进展；持平、问题增加或无法证明收敛时停止自动修复，旧记录无稳定 issue_id 时以数量减少判断。不因出现新问题无限加轮次。
- 审计未调用 SubmitVerdict 属于协议未完成，不是实现缺陷：仅补交一次，最多 4 轮 / 120 秒 / 12000 预算 Token；仍未提交则停止，不派执行者凭空返修。循环检查点仍使用自身 SubmitLoopDecision 契约。

## 节点工具

### 批量审阅与返修（阶段5故障的通用约束）

- 开跑前做“验收要求→负责节点→实际工具→可交接产物”的检查。需要写入返修的循环声明 requires_repair=true 和 repair_node_ids，目标必须是循环内有写入能力的 implement；审计员不能给自己加写权限。纯只读独立审核无需虚设执行节点。
- 固定清单按稳定 item_id 持久化，模型只做当前少量工作项，完成一项立即提交。ReviewWorkQueue 的 record 是宿主台账提交，不是业务文件写权限；PNG/PDF 用 ReadAuditArtifact，文本用 evidence 动作取宿主引用ID。JSON按页选择；不反复全局搜索、复制哈希、从长聊天重建进度。
- needs_repair/unknown 是已审阅但未解决，不是新待审页；交 ReadReviewQueue 工作单给执行成员，在候选副本最小返修/补证，再定向复核。只读节点自循环不能完成“修复全部错误”；缺陷出现但没有返修能力时要求计划修订，不让模型继续空转。
- 业务验收与调度恢复分开：Jev（或用户所选审核模型）选择可执行路径，不给不存在的工具授权、不替代审阅、不代签用户门禁。有正常批次进度时不必反复请求恢复决策。
- 普通“继续任务”保留队列；“重跑后续”会归档队列并重建进度，二者不可混称。修订先比较合同、范围、证据指纹；只能迁移兼容记录。批准修改图不等于启动执行，更不等于批准原任务验收。
- 审核口径必须一致：是否忽略页眉、广告、格式差异写入合同；修复初筛误报不能私自缩小已确认清单。用户签认放在真实 gate，不埋入机器自循环的终止条件。详细操作见本 skill 的 references/batch-review.md。

默认使用角色工具契约；节点 `tools` 用于聚焦该节点的能力，不限制协助会话；确需禁止的危险能力用 `deny_tools` 排除。协助仍受全局权限和 Auto 审查约束。显式 `[]` 禁用可选工具。人工交互与协议报告工具由运行器保留；审计、循环 reviewer 的只读边界及候选副本限制不可覆盖；manager/planner 显式启用 Bash 时仍经过现有权限审查，不能称为只读命令沙箱。可信插件的角色定义可声明 kind；画布从 /api/orchestration/kinds 获取，内置 kind 映射不可被图数据覆盖。

代码候选返修按“定位失败测试 → 最小修改 → 定向验证 → 交付 diff”处理；文档/图像任务保留对应证据流程，其他任务使用通用交付检查，不套用论文修图步骤。候选没有 .git，也不连接原项目依赖目录。执行者可用 VerifyCandidate 运行 pytest / unittest / npm_test，提交候选相对测试路径；工具按语言首次复制独立依赖快照，返回实际目录、退出码、日志、候选哈希和基线 diff。它执行测试代码，仍须命令权限审查，不是只读工具或操作系统沙箱，冻结验收的审计员只读这些证据。

Python 使用原项目 .venv/venv 解释器及复制的依赖，但禁用 .pth / editable-install 钩子，优先加载候选根目录和 src；无项目环境时仅可尝试标准库 unittest。Node 使用候选 node_modules 独立副本。不会自动安装依赖；声明变更、依赖缺失、越界链接、超过 100000 文件 / 2 GiB 时明确报告环境缺口，不反复运行同一失败命令。依赖快照不属于业务交付物，不能凭原项目测试通过认定候选通过。

## 交接与经验

manager/planner/executor 可用 SubmitHandoff 提交 summary、artifacts、decisions、open_items、evidence；未提交会根据实际文本和工具记录回填，不代表验收通过。直接下游拿到结构化交接与正文，汇总额外获得全图摘要；返修保留原方案和本节点上次交接。

节点重试、定向返修和普通继续额外带最近 3 次尝试的有界记忆：结果状态、摘要、最近 3 条失败验证命令及输出尾部、实际改动文件和未完成项；旧快照可从工具记录提取。先核验保留文件，再选不同方法；记忆不是新的授权，也不能将未知结果的不可逆操作自动重放。

经验只注入匹配当前图、节点或角色的 active 条目，每节点最多 8 条；与当前任务冲突时服从任务。运行反思只产生 pending 建议，经用户确认才启用；“记住：”“以后：”“经验：”补充可直接保存为用户经验，可用 @node_id 指定节点。画布经验页可查看、确认、启停或删除，成功命中率仅供判断，不会自动淘汰。

人工等待默认 20 分钟转 paused，只暂停发问节点所在分支并保留待答请求；恢复后重放同一问题，不默许通过。模型流无响应和行为停滞是不同故障：前者由供应商看门狗结束，后者先提示换方法，再次触发才停止；均不算验收成功。

## 计划、配置与运行

- 阶段图的生成完成与执行就绪分开：候选快照完整后仍可能有重复定义、结构错误或待选业务版本；以当前 readiness 和诊断为准。
- 批量循环可声明 `mode=foreach` 和 `items`（1–100 个唯一 item_id 与明确 goal）；批内审查只验当前项，循环 criteria/exit_condition 验整个队列退出。
- 修图允许宿主合并重复参数、循环和依赖。原条目整体退役并保留来源；有分歧时预览选择保留版本，不能改写锁定正文来隐藏冲突。合并不执行节点任务、不自动保存画布。

- 阶段目标 goal 是简短结果；plan_brief 分开保存 summary、known_inputs、open_questions、steps、outputs、acceptance。已回答的问题不要重复询问，运行时生成的长计划不要反灌为目标。
- 多个运行参数值使用 `type: list`，由宿主按项收集并以数组传递；不要将多个值塞进单个文本字段。
- 模型绑定使用 provider_key / model_id / effort；草稿可以 bind_later，确认执行前需补齐非 gate 节点。节点类型不是权限凭证，委派仍服从项目规则。
- 当前 spec 是编辑依据，画布是其表现，ControlPlan 是派生调度说明，不是第二套执行脚本。抽图、回填和保存不会自动开跑。
- 运行与检查点按 run_id 独立保存，当前进度以最近实际启动或恢复的任务为准，不因旧任务仍受阻而切回旧图。恢复须匹配当前确认的图；替换方案不应混入旧节点或删除旧运行历史。审计基准保持已确认快照，返修针对候选成果。
