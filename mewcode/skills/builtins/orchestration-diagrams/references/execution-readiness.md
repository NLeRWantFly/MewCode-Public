# 可执行构图经验

将用户要求对应到宿主支持的执行字段。当前任务、模型配置、runtime_semantics、字段白名单和本次输出协议优先；本页不新增业务要求、数据外发授权或预算。历史案例的路径、节点 ID、模型名称与数量不作为默认值。

## 保留业务主线

以当前版本的图、原始用户要求和明确采用的决定为基线。保留未要求变更的来源、稳定 ID、模型绑定、验收、人工门禁和循环合同；提出具体字段差异，写回由宿主校验版本与基线。历史进度、修图聊天、校验错误和启动异常不能提取为业务阶段。只分析本批来源，不把经验文案冒充用户引文，不重放旧历史恢复已删除内容。

## 设计初期先构建节点，再探索

按“构建节点 → 探索 → 收敛验证”推进。读取现有规格后，先保存已明确的节点、输入输出、依赖和待探索事项；草稿允许尚待完善，不能把完整用例、回归测试或业务试运行通过当成新增节点的前置条件。用户给出节点 ID 时精确定位并复用，改名、移动或调整属性不重新编号。

探索围绕当前未知点，优先读取已有材料和有效证据，只做足以决定下一步的最小探测或代表样本。把输入、方法、结果与适用条件写入已有规格或节点说明；条件未变时直接复用，得到有效结论就继续完善图。不要每补一个节点、每轮讨论或每次改名就重新跑用例、全量回归或同一试点，也不要为设计过程中的每次检查增设业务节点。

方案和关键接口收敛后，才安排必要的验收用例与相关回归。重复验证需由相关实现、输入、模型、环境或验收变化、新失败，或用户明确要求触发，并限于受影响范围。初期保留轻量字段、引用与依赖检查；最终保存仍需结构与独立覆盖核验，实际批量执行前仍需代表性试点证据和既定业务验收。用例与试点可先设计为后续节点，不要求在构图对话里全部执行；有效的既有试点证据可复用。这一节约束设计顺序，不改变用户目标、验收或授权。

## 职责与模型落实到字段

模型要求写入实际 `model={provider_key,model_id,effort}`（图条目中为 `node.data.model`），引用当前 `available_model_routes`；正文中写模型名称不足以绑定。保留用户已选路由和推理档位；指定路由不可用时留下具体 capability 缺口，不猜供应商、不静默降档。配置可解析仅证明配置存在，视觉与工具能力仍需代表性试点。

父节点只组织已有独立子阶段时使用 `execution_mode=coordinate`，实际工作由子节点的绑定、输入、产物、验收和显式依赖承担。`parent_id` 表示层级，不建立执行依赖，也不证明委派或写权限。避免父子重复处理整段任务。

## 主模型监管与有边界的交接

编排中的主模型负责方向和验收：执行前核对目标、方法、输入范围、禁止改动、交付物与验证方法；阶段交接后依据实际变化、产物及验证证据评审。用实际 `plan`/主控节点和独立 `audit`/审查节点、模型绑定与依赖表达职责，不能只在正文承诺“有人监工”。沿用用户选定的主模型路由，不按名称猜测能力，也不替换执行路由。

优先复用既有计划与审查节点，一次检查可以覆盖一组相关阶段；仅在阶段交接、明确里程碑、方向偏离或原有证据失效时重新核对。不要为每次工具调用新增监管节点，不回读全部历史，不重复完整执行任务。纯协调父节点不重复子节点制作；人工确认、执行模型自评与最终汇总不能替代独立质量评审。成功路径必须有结果审查，不能只给失败分支安排审查，也不能让可选分支跳过验收。

交接携带本次范围、产物位置/版本、实际验证命令或方法及结果、未关闭问题；大内容按需读取。返修只针对有位置、证据与关闭条件的问题，复审关注变化集、未解决项及相关回归。缺证据保留未通过状态；执行完成不等于审查通过。改变目标、验收、权限、预算或模型路由由主控处理，不能通过返修悄悄扩大范围。宿主就绪检查仅检查结构覆盖，主模型仍须判断方法与结果是否符合目标。

## 独立结果与循环入口

用户要求独立解答或独立评估时，让两路接收同一任务入口，各自产出后共同进入汇总/裁决；不要把第一路答案连接为第二路输入。独立性不要求同时执行，串行/并行服从宿主限制。逐项重复分发时，将共同入口纳入循环体和 `entry_node_id`，下一项回到该入口，保证每项都派发两路。

循环回边使用 `condition=loop` 并配套宿主循环合同；检查点、执行/返修成员、退出验收和循环外汇总必须明确。按用户选择和实际模式配置预算，不照抄旧案例、不因继续或重试重置已消耗的额度。批量任务使用稳定工作项与持久化进度，细节见同目录 `batch-review.md`。

## 选择要真正控制调度

可选功能或交付方式先声明 input，再给互斥边 `input_when={input:参数名,equals:选项执行值}` 和同一 `branch_group`。正文描述“启用/禁用”不能分流，两条 `pass` 边默认都会匹配。参数的 options.value、条件值、收集阶段与实际可达路径一致；未知值等待收集，不推定为关闭或允许。保留候选成果应走到候选交付，正式发布才进入发布阶段；仅在当前任务需要这类选择时设计相应分支。

## 技术问题、业务取舍与阶段参数

普通技术结构由 AI 在宿主允许范围内补齐，设计假设与用户事实分开。真正需要用户取舍的问题在现有构图讨论中提供 2–6 个有影响说明的选项，使用 `{value,label,description,recommended}`；推荐不自动选中，暂定偏好不等于采用。

运行参数用 `collect_at` 留到实际需要的阶段，条件必填用 `required_when`；关联问题通过 `input_id` 指向同一参数，避免重复询问。没有默认值的后续参数不必阻塞生成图，但必须在使用前收集。费用、内容外发、发布范围等决定不能由合理默认代答；参数回答不替代人工 gate 签认。

## 生成时排雷：运行中无法自愈的结构

以下结构在运行时只能暂停或反复问人，必须在生成、补全和审查时排除。它们约束图的设计方式，不新增业务要求、授权或预算；与用户明确要求冲突时，说明影响并请用户取舍，不静默改动。

1. 角色与工作量匹配。plan 节点只做有界调查：一次性清点全部输入的元数据（数量、页数、格式、文本层等宜用脚本或批量工具取得）、选取明确数量的代表样本、制定方案。逐页、逐项、全量的读取或处理放进 implement 节点或带稳定工作项的批量循环（见 `batch-review.md`），并写明批大小。plan 的验收不得要求“每页/所有项均已查看”。需逐个读取的对象超过一个执行分段能完成的量（约数十项）时，必须拆成持久化工作项。
2. 验收在本节点闭合。每条 acceptance 都要能由本节点 outputs 和已声明工具在本节点内举证。出现“全部/所有/完整/不得缩减”时，同时写明有限对象集合（来自哪个运行参数或上游产物）和核验方法（脚本统计、清单对账）。依赖下游结果或用户决定的事项放到对应节点或 gate，不写成本节点验收。
3. 输入单一来源。known_inputs 写来源而不是占位：运行参数写“运行参数 <name>”，上游产物写“<node_id> 的 <产物>”。已由运行参数或上游提供的信息不得再写“待提供/待确认/待补充”；真正缺失的写入 open_questions 或声明为运行参数。同一事实不在 goal、known_inputs 与参数默认值中保留不同版本。
4. 多值运行参数。多个值声明为 `type: list`，默认使用换行分隔；需要其他分隔符时显式声明 `separator`。每项独立填写和提交为数组，不把多个值拼成一个文本参数。
5. 执行环境前置。需要脚本、解析 PDF/图像/数据库或运行测试的工作，在首次使用前安排环境准备与验证：放在同一 implement 节点的第一步或独立前置节点，使用 PreparePythonEnvironment / RuntimeDoctor 准备项目根 `.venv`，验收为解释器路径、依赖名称及版本的实际输出。不在产物目录或候选目录另建虚拟环境；一个项目只保留一个项目环境。只读探测也写明所用工具和预期输出。
6. 能力在进入循环前验证。进入批量循环前，用试点节点在 1–3 个代表项上跑通循环内用到的全部工具、模型（含视觉）、环境和写入路径，并把试点产物作为循环入口的已知输入。运行中发生能力或环境变化时，循环成员通过 RequestAssistance 获取主模型协助，宿主核验清除凭证后接续；权限与业务决定仍需用户处理。
7. 探测与副作用分开。只读探测（版本、导入、页数统计）用验证类工具或宿主确认的丢弃式执行（RunVerification，或 `Bash` 的 `publication="discard"`），写成独立、可重复的命令或脚本文件。宿主依据实际策略判定只读效果，丢失回执时保留一次重试额度；混合写入、安装或无法证明只读的命令先由协助会话核验效果，不自动重放。有副作用的命令写明输出路径，便于事后按文件核对。
8. 工具授权宽进严出。节点 tools 用于聚焦该节点的能力，不限制协助会话；确需禁止的危险能力用 `deny_tools` 排除。审计和 reviewer 的只读边界保留，返修通过 `repair_node_ids` 交给有写入能力的 implement。
9. 有效声明备用节点。启用 `on_blocked: fallback` 时，`fallback_node_ids` 必须引用存在且非自身的节点；字段声明后运行器会按配置调度备用路线。长任务仍要拆分并提交可接续的阶段成果。
10. 人工决定前置、集中。可预知的业务选择、内容外发、费用和路径，在 start 或早期 gate 收集。运行中确需用户选择、授权或提供无法取得的材料时，可在所在分支提问；等待只暂停该分支，其他独立分支继续。不要把人工确认嵌入循环退出条件。
11. 分段可接续，进展可计数。每个节点在一个执行分段内就应提交阶段性 SubmitHandoff（inline_outputs 或产物文件），持续产生宿主可计数的进展：业务文件写入、台账记录、内联产物，以及具有新内容哈希或新页码的 ReadAuditArtifact、ReadFile 结果。重复读取同一证据不增加进展；读取结论及时落成产物或台账。
12. 审查不按证据类型拆分。同一审查对象只设一个 audit 节点，节点内按证据类型选择工具（文本 ReadFile、像素 ReadAuditArtifact 或 InspectVisualEvidence、命令 RunVerification）；需要像素证据时，确认节点模型支持图片或已配置看图能力。

13. 授权与能力先于使用。不得把内容外发、联网、工作区外写入的授权门禁或能力准备放在需要它们的节点之后；运行开始收集或所有执行路径前置门禁均可。需要观察像素的规划节点也须显式声明看图能力。配置、模型方案、用户口头意愿不是工具授权；具体授权经宿主确认并传入后续节点。

交付前逐节点自检：角色与工作量匹配；验收可在本节点举证；known_inputs 无占位；每个 step 都有已声明工具可完成；授权、能力与环境准备在首次使用之前；批量循环之前有试点；人工决定位于 start 或 gate；没有依赖无效字段。有任一项不满足时修正后再交付，修不了则写出具体诊断，不交付带雷的图。

## 修正后按当前版本核验

局部补全遵守 `editable` 和 `completion_contract`；不能为了通过而改锁定要求、删依赖、弱化验收或清除问题状态。允许范围不足时保留具体诊断，不扩大修改权。覆盖核验只查当前明确要求是否由实际节点、约束、分支、参数或确认点兑现；本页本身不是新增要求。

改图或采用决定后，旧覆盖结论失效。新一轮缺口要按新诊断继续处理，不能因为旧补全游标已完成而跳过；旧成本、回执与来源进度仍由宿主保留。字段/协议错误依据反馈修正，能力缺失和业务取舍分别说明，不以无界重试替代解决。

## 明确验证层次

同名运行参数、同 loop_id、同条件依赖使用已有条目 ID。遇到 `duplicate_business_key`，先按诊断中的 entry_ids 合并重复定义：相同 data 由宿主确定性退役重复副本；data 有分歧时展示版本并由用户选择。保留退役条目的原文、sources 和 superseded_by。对话试修只读不等于不能改图：输出修订单后须预览并采用，采用只更新候选图。旧 ticket 重签发后不可复用；缺少检查条件的 skipped 项不得说成通过。

有限批处理使用 `mode=foreach`、冻结 `items=[{item_id,goal}]`，每項目标应是文件、章节或明确页码范围，不能用一项代指整本书。每项/每批审核写在批内节点 acceptance；criteria 与 exit_condition 写队列级完成条件。`batch_audit_scope` 提示批内全量验收与队列退出语义不一致，须核对后修订，不能删验收来过检查。

分别记录：结构/字段/循环/绑定及转换检查、当前图的独立语义核验、实际前端请求到启动边界的隔离回放、授权后的代表性试点与业务验收。保存图、配置可解析、启动回调被调用都不证明业务完成。隔离验证使用模拟模型，不发送业务材料；真实处理的外发范围、费用、工具权限与人工签认按当前任务落实。报告只写已验证的层次和仍待完成的事项。
