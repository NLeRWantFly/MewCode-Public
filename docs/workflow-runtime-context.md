# 工作流 Skill 与增量运行概要

节点启动或恢复时，宿主从冻结流程、当前阶段合同和实际启用的工具参数定义生成版本固定的 Skill，主动加载精简入口，并将完整包写入节点工作目录的 `.mewcode/workflow-skills/<version>/`。运行进度不参与该版本计算；概要绑定节点、输入版本、尝试、epoch 和 Skill 版本，绑定不匹配时重新投影。

入口保存流程地图和执行规则。大地图、当前阶段合同、工具协议分别通过 `ReadWorkflowContext` 的 `plan`、`stage`、`tools` 分页读取；`requirements` 提供本次提交要求，`submission` 返回最近提交的完整参数草稿与宿主回执，`current` 返回最新概要。每页包含来源版本和下一游标，来源变化后须重新核对。包只包含流程规范，不包含其他独立节点的运行证据。

宿主根据每轮和工具回执更新概要，不额外调用模型生成摘要。概要从当前存储状态计算，已清除的用户问题、权限请求不会被恢复前的快照重新带入。读取证据、产物变化、提交被接收、核验完成分别计数；概要本身既不产生进展，也不产生授权或验收结论。

执行以最新 state 和本轮增量为准。续接提示从当前状态重新投影，不复制旧概要的下一步；旧拒收原文只保留在精确回执中，不作为执行指令重新注入。已有且版本有效的草稿、回执与证据直接复用，只对当前缺失或过期的字段、来源给出定向读取入口。已被后续成功回执取代的失败不再进入当前失败方法清单。

## 上下文预算与恢复

每个执行段保留概要基线，在消息尾部追加变化。导航概要按 6000 字符控制，单次增量不超过 1600 字符，最多保留四条增量；超过数量或体积阈值后合并。原始要求保留在冻结任务提示和分页源中，不把截断摘要当成完整要求。上下文压缩的预算预览与正式恢复调用同一恢复入口，恢复操作不改变概要版本或业务状态。

常规增量轮次保持已有前缀；合并和压缩会改变前缀。上述限额约束概要层，整次请求仍由现有上下文管理器统一计算工具、历史、证据和输出预留。实际服务端缓存命中率须通过真实运行的用量回执确认，离线测试不证明命中率。

## 提交纠错与等待状态

审计提交区分参数错误、引用不匹配、缺少证据、质量问题和服务故障。必需答复为空却多带旧引用时，明确要求删除多余引用，不再提示用户尚未回答。原始拒收原因和草稿持续保留到后续提交被接收；轮数耗尽或归档读取不能覆盖该原因。

字段纠错复用现有检查点与预算，结束回复前最多补充两次纠错机会，既有权限与质量门禁继续生效。归档、授权和概要读取被识别为只读观察，重复读取不算业务产物进展。界面在汇总实际待办后再判断是否等待用户；没有实际待答项的技术暂停显示为已暂停。

恢复旧运行时，缺少错误分类的拒收回执保留原文。宿主使用当前工具的同一套引用校验规则重新检查已保存草稿，将源版本变化、缺少引用和多余引用投影为当前纠错指引；不从旧错误文字推导授权或用户未决事项。该投影不提交判定、不改写旧回执，也不把引用匹配视为质量验收通过。调度器只复用与当前节点、输入版本、尝试和 epoch 一致的概要。

冻结循环中由 auditor 担任的检查点，运行工具限定为证据读取与宿主判定提交。旧计划未填写外部能力时，宿主为它生成空能力清单，允许读取当前证据并提交 `SubmitLoopDecision`，避免在模型启动前误报环境故障。空清单不授权写文件、命令、联网抓取或图像外发；这些操作仍按原有逐调用权限和能力校验处理。非检查点、非 auditor 节点及已有显式能力声明保留原规则。

## 验证入口

`tests/test_workflow_context.py` 覆盖错误引用、三十次重复读档、草稿恢复与纠正提交、140 轮概要体积、前缀稳定、分页与独立证据隔离，以及两种协议下压缩后的上下文恢复。`tests/test_human_waits.py` 覆盖问题和权限恢复后的概要状态；`tests/test_stage_checkpoint_performance.py` 检查轻量写入与完整投影一致。

专项测试及对照结果保存在 `outputs/workflow-skill-20261101/`。执行离线验证时设置 `MEWCODE_OFFLINE_TEST=1`。

## 业务进度与问题画板

Agent 使用现有 `report_step` 汇报业务位置，`progress` 包含稳定的工作范围 `scope`、单位 `unit`、当前位置 `current`、已知总量 `total` 和有依据的已处理数量 `completed`。例如书名、第5页、共110页、已处理4页。总量未知时省略；位置可以因返修回退，循环轮次与页数分别显示，各阶段或各本书的计数不相加。

`issues` 每次最多更新5项，使用稳定的 `scope/id`，注明用户可定位的 `location`、内容问题 `message`、处理动作 `next_step` 与 `open/fixing/resolved` 状态。下游可以反馈“第5页第二个公式缺少分母”，修订者沿用同一标识更新；画板保留最早反馈来源。`resolved` 显示为“已修正 · 待复核”，不能代替原业务验收。模型编号、内部节点ID、哈希和异常代码不作为画板正文。

汇报从成功工具回执进入宿主状态，绑定本节点的输入版本、尝试与epoch；每节点保留最新概要及最多16项问题。过期或失败调用不能覆盖当前汇报。保存、重启和增量投影保留相同显示；汇报不新增账本进展、不通过验收或授予权限，也不额外调用模型整理。

画布上方显示正常字号的业务进度和问题，循环区域使用独立边框、回边、轮次与当前步骤提示。定位当前步骤保持可读缩放，数量变化不重置用户视角；详情保留内部诊断信息。只有实际取得的数量才显示进度条，旧运行尚无数量汇报时明确等待汇报。

`tests/test_work_progress_board.py` 覆盖数量边界、当前绑定、问题更新、来源保留、持久恢复、增量投影及真实Agent适配链；`tests/workbench_progress.cjs` 覆盖循环范围、数量语义、问题状态、跨任务隔离、定位及视角保留。`tests/serve_loop_progress_preview.py` 提供使用正式工具、存储和前端组件的独立交互验收样例，不写入现场业务运行。

本轮后端 188 个不同用例、前端 32 项检查及浅色、深色、窄窗口的浏览器交互验收通过。新版应用重载后，原任务保持同一运行，从 attempt100 接续到 attempt101；活动复核节点的实际 Skill 与工具定义已包含新的汇报协议，工作台数据包含真实循环及轮次。71 份固定成果、21 份交接证书、151 条原回执及要求、模型、授权最终核对一致，证据位于 `outputs/loop-work-board-20261102/`。

客户端窗口正常关闭后进程未退出；确认任务已暂停、无活动节点或未决调用且检查点一致后，清理该空闲实例并通过原安装程序重新打开。原生截图接口仍报 `window capture timed out`，浏览器样例不计为原生画面验收。现场数量与具体问题需等待实际 Agent 汇报；样例中的书名、页码与问题不是当前业务成果。

## 普通独立复核与返修批次

“交付当前版本→两路独立复核→按结论返修并再次复核”这类流程可以只使用普通阶段产物，不必具有逐项返修台账。此前运行适配层只要发现循环和下游审查者，就把独立复核入口标成 `RequestVerification`，无条件装配工作单和候选预检提示。该工具本来只接收已提交的返修批次，因而空台账使正常的普通复核被误判为缺少前置条件；旧助手报告再经恢复概要回流，会把这项宿主提示误传为用户要求。

`experts/review_protocol.py` 现在从冻结图、当前循环和真实台账统一解析协议。普通阶段提交仍是图中下游的主要调度入口；只有已初始化台账才提供批次提前交接。没有台账时不挂载 `RepairWorkBatch`、`RequestVerification`、`VerifyArtifacts`，不提示创建候选编号；有真实候选时仍执行原有批次、指纹、证据和渲染检查。损坏或合同过期的台账保持失败关闭，不能按空台账继续。

实际协议同时进入能力清单、`ReadStageResult('@review_protocol')`、节点概要和接续提示，并绑定输入版本、节点尝试与 epoch。没有台账且已明确失败的旧批次方法只提供一次纠正指引；旧原文和回执保留，真实缺陷、用户问题、权限请求、未知执行效果与质量门禁继续有效。普通交接仍须完成当前节点合同，工具接收不等于业务验收通过。

`tests/test_review_protocol.py` 覆盖两路独立复核没有批次的实际 Web 适配链、普通 DAG、混合队列、旧方法纠正、绑定漂移、真实边界保留、未改文件的再次复核及中断恢复。原批次与核验测试继续检查未提交、过期、外部批次和不合格候选不能通过。验证证据保存在 `outputs/review-protocol-20261102/`。

本轮共 243 个不同后端用例通过，结果按用例标识去重，以最后一次相关回归为准；原失败报告保留。修正了旧测试对 `complete/pass`、恢复历史存储位置和有界重试的过期断言，没有变更对应生产门禁。Ruff 和变更文件的 `git diff --check` 通过。实际服务的恢复及推进须单独核验，不能用离线用例代替。

## Provider 实际模型与推理档位

模型列表可将 `gemini-3.8-flash-high` 合并展示为 `gemini-3.8-flash`，但该分组实际发布的 SKU 仍是执行依据。只提供带档位后缀 SKU 的 Provider，列表中的可选档位与默认值按其真实目录收窄；未发布的档位在构造模型客户端前被拒绝，不能把通用模型能力目录中的档位拼成不存在的模型名。提供基础模型 SKU 的服务继续使用基础模型加单独的 effort 参数；只有明确发布过的后缀 SKU 才替换请求模型名。

现场 Gemini 分组只发布 `gemini-3.8-flash-high`；此前融合节点误选 WorkBuddy 路由，切换分组后又因沿用 medium 而请求了不存在的 `gemini-3.8-flash-medium`。已按用户指定的分组使用其实际提供的 high，并通过原应用的节点模型入口记录调整。`model_catalog.py` 与 `model_registry.py` 统一约束列表、默认档位及实际请求；没有改写 Provider 全局配置。

新增两个用例先复现错误，修复后模型目录、路由、桌面配置与节点模型联合回归 112 项通过；与前述 243 项合计 355 个不同用例。错误请求、原检查点和两次路由调整的回执保留在同一证据目录，实际派发与业务核验分别记录。

正常重启加载后，实际模型目录仅提供 high；原运行已从同一检查点恢复，Gemini 路由取得真实成功工具回执，节点加载普通阶段交接协议且没有批次专用工具。最终核对 71 份固定成果、21 份原交接证书、128 条原回执（包括正常迁入尝试归档的回执）、原要求和授权均保留；只调整用户指定的融合节点模型。授权清单的缓存指纹在首次运行预检时短暂变化，其逐字段差异及不可变事务来源已核对，实际调用后恢复为原指纹。证据为 `verification.json` 和 `live-preservation-final.json`。实际业务的独立复核和质量验收继续由原合同约束。
